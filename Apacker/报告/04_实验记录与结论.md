# 实验记录与结论

按时间顺序记录做过什么、哪些成立、哪些失败，以及未解问题。

## 阶段 A：纯静态侦察（只用样本 + Ghidra）

| 动作 | 结果 |
|---|---|
| 打开样本、看节表 | 11 个节，4 个随机节名（`.AXJvbGt/.PELvaOG/.WQQJChj/.GukYJZE`） |
| 数据目录 | `Import=0`、`IAT=0`；`.text` 熵 7.9988 |
| 反汇编 `.text` | 立即 `halt_baddata` → 整段加密 |
| 入口分析 | `entry` 只有 `call FUN_14005a840` → 桩的 stage1 |
| 找 crypto 常量 | AES S-box ×2、SHA-256 轮常量、CRC32 表 ×3 |
| 解出 stage1 逻辑 | `AKPH` 校验 → 生成 32B 密钥 → 解出 `AKPC` → 建 ctx → `VirtualProtect` → 跳 stage2 |

**结论**：确认是"两段式 + 页级加密 + 运行时重建导入"的壳。

## 阶段 B：动态取证（不依赖调试器）

当时的调试器通道被审批策略挡住，于是自己写了内存取证脚本（`脚本\region_dump.ps1` / `final_dump.ps1`）：

- 非提权启动样本 → 轮询 `ReadProcessMemory` → 检测到 `.PELvaOG` 出现 `AKPC` 头就 `NtSuspendProcess`；
- 容错 dump：`VirtualQueryEx` 遍历地址空间、对 `PAGE_NOACCESS` 页临时 `VirtualProtectEx` 读取；
- 同时抓模块基址表（`modules.json`）。

**观察**：`.text` 只有**已执行过的 ~50 页**是明文，其余 10 页仍是密文 → 证实"惰性页解密"。

## 阶段 C：复现解密（关键一步）

从 `FUN_14005a840` 反推：

```
key[i] = ~T1[i] ^ T2[i] ^ k0 ^ k1      (T1/T2 在桩节 +0x38/+0x58；k0/k1 来自头部 key 值)
IV(页) = [key值 4B LE][00000000][页VA 4B LE][00000000]
```

用 AES-256-CTR 复现后与内存里壳已解的页比对：**除壳还没来得及解的那页，其余 50+ 页逐字节一致**。
→ `.text` 57 页全部解出，熵 7.9988 → 6.445。

**这是整个任务的转折点**：从"部分页"变成"全量明文"。

## 阶段 D：OEP 与导入表

- OEP：沿调用链 `0x11B40 → __scrt_common_main_seh(0x119C0) → main(0x6520)`，并用 `AKPC+0x0C` 交叉印证；
- 导入：运行时 `.rdata` 的 `0x3A000~0x3A3F8` 是壳重建的 IAT，逐个指针反查「模块 + 导出 RVA → 名字」，得到 **115 项**，用系统 DLL 导出表校验 **0 缺失**。

## 阶段 E：重建可运行 PE（失败与部分成功）

把 `.text` 换成明文、新增 `.idata`、EP 改成 `0x11B40`，加载器却**不填充位于 `.rdata` 起始（0x3A000）的 IAT**，程序执行到第一个导入调用就跳到 0（`0xC0000005`）。

对照实验（全部实测）：

| 变体 | 结果 |
|---|---|
| IAT 在原位置 0x3A000（`.rdata`，R） | 不填，DLL 都不加载（模块表只有 4 个） |
| `.rdata` 改成可写 | 仍不填 |
| 描述符挪到 `.data` | 仍不填 |
| 描述符也放进 `.rdata`（与 IAT 同节） | 仍不填 |
| Import Size 补终止项 / 文件尾部补 padding / 清 HIGH_ENTROPY_VA / 去掉 IAT 目录 | 仍不填 |
| `FirstThunk` 挪进 `.idata` | **加载器开始处理**（抛 `0xC0000139`，因为落点压到了字符串表） |
| 对照：正常 exe（IAT 在 `.idata`）走同一流程、EP 改回 OEP | **正常运行** |

**结论**：问题与"加密"无关，是 PE 重建时的 IAT 布局问题；文档里保留为未解问题（见下）。

## 阶段 F：引入打包器本体做旁证

拿到 `apacker_cli.exe` 后：

- `info/verify` 确认 `imports_removed=1`；
- PDB 印证了 `aes256_ctr_nonce(u32,u32)`、`PageInfo/SectionInfo/...` 数据结构；
- 用 `encrypt_code=0 + obfuscate_imports=0` 重打包，验证"加载器处理导入表"的行为差异；
- 用 `encrypt_code=0 + obfuscate_imports=1` 产出**代码明文 + 桩只解析导入**的可运行版本
  （`产物\Campus_Network_learning.plaincode_runnable.exe`，实测输出与原版一致）。

> 注意：最后这条不是"脱壳"，只是"关掉加密的重打包"，桩仍在。

## 阶段 G：做成通用脱壳机

`脱壳机\apk_unpack.ps1` 把上述流程参数化：

1. 逐节找 `AKPH` 魔数 → 定位桩节；
2. 解析 AKPH（stage2 VA、长度、key 值）→ 派生 AES-256 密钥；
3. 解 stage2 → 校验 `AKPC` 魔数 → 读 OEP / 页数 / 页表偏移；
4. 按页表逐页 AES-256-CTR 解密（IV 由页 VA 生成）；
5. 输出明文镜像（EP=OEP）+ `.text.bin` + `report.json`。

自检：样本 1 的 `.text` 与之前独立验证的版本**差异 0 字节**；样本 2 自动识别成功。

## 未解问题（1 个）

**Windows 加载器不回填"位于 `.rdata` 起始的 IAT"。** 已排除：节属性（改了可写）、描述符所在节（换过 3 处）、
Import 目录大小、DllCharacteristics、IAT 目录、文件 padding。唯一有效线索是"把 `FirstThunk` 放到 `.idata` 就会处理"。

两条收尾路线：

1. **IAT 迁移 + 引用重定向**：把 IAT 挪到新节（如 0x70000），把 `.text` 中所有引用 `0x3A000~0x3A400`
   的 RIP 相对指令的 disp32 改指新地址。需要精确枚举引用（Ghidra xref 或 `ig5_run_idapython` 一次导出）。
2. **保留桩**：接受 `obfuscate_imports=1, encrypt_code=0` 的产物 —— 代码明文可读，桩只做导入解析。
