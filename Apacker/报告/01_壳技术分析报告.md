# Apacker 壳技术分析（配合样本 Campus_Network_learning.exe）

> 样本 SHA-256: `85d37375932ec0ef5199c3ca510c1219dcb3fc5d73000f2246ea40e87d0ad1e8`
> 打包器: `D:\sec\Tools\Tool_List\apacker_gui\apacker_cli.exe`（GUI 同源，`apk::` 命名空间，Qt6 + LIEF）
> 本文件基于：packer 二进制字符串 / `apacker_cli.pdb` 符号 / 样本 stub 反编译 / 运行时内存 dump。
> 标注：**[观测]** = 代码或数据直接证实；**[推断]** = 由结构或行为推出。

## 1. 定位与总体设计

Apacker 是一个**自研 x64 PE 加密壳**，不是商业保护器（无 VM、无虚拟化），定位接近"轻量反 dump + 反调试的加密壳"：

```
原始 exe ──LIEF解析──> 选节 AES-256-CTR 加密 ──> 写运行时配置(AKPC)
          ──> 清空导入表(可选混淆) ──> 追加 stub 节 + 配置节 ──> 输出
```

**[观测]** packer 自身的流程日志（`apacker_cli.exe` 内字符串）：

```
parsing input PE
collecting sections, imports and relocations
encrypting selected sections with AES-256-CTR
building encrypted runtime config
appending stub and configuration sections
clearing import descriptors, ILT, IAT and names
writing packed image
output entry point is not inside the stub section     ← 自检
output still has an import directory                  ← 自检
output lost the config section                        ← 自检
```

**[观测]** PDB 里可见内部符号，说明 stub 是构建期生成的字节数组嵌入的：

```
apk::kStubBlobData / apk::kStubBlobSize / apk::kStubEntryOffset / apk::kStubHeaderOffset
E:\ai_project\dsh\Apacker\build\generated\stub_blob.cpp
E:\ai_project\dsh\Apacker\src\core\stub_blob.hpp
struct ApkStubHeader
```

配套工具 `apk_stub_extract <apkr_stub.dll> <out.cpp>` 就是把这个 stub DLL 转成 C++ 数组源码。
**[观测]** stub blob 以明文嵌在 `apacker_cli.exe` **文件偏移 0x6AD50**（长度与样本 `.AXJvbGt` 节一致，0xA73D），
开头即 `ApkStubHeader`：`01 00 00 00` … `+0x10: "AKPH" 01 00 00 00` …，后面是待重定位的指针/偏移修复表。

## 2. 加密算法与页粒度

| 项 | 值 | 依据 |
|---|---|---|
| 算法 | **AES-256-CTR** | [观测] 内联 AES（S-box 0x140058610/0x140058C30，MixColumns 0x1b，15 轮）+ CTR 计数器递增 |
| 密钥 | 32 字节，由两张 0x20 表与头内 4 字节值派生：`key[i] = ~T1[i] ^ T2[i] ^ k0 ^ k1` | [观测] `FUN_14005a840` |
| 密钥材料 | 样本中为 `B8 1C 94 00`（`k0=0x00,k1=0x94`），最终 key = `DFE1C48C 43D6F18C F01D0398 D2905D14 AA2591A2 6D0111C9 FD321AD0 25587FD6` | [观测] 本机复算 |
| IV | 16 字节 = `[4字节key值][00000000][页VA(小端)][00000000]`，**每页独立** | [观测] `FUN_14005d450` |
| 粒度 | 0x1000 页，逐页按页表条目长度解密 | [观测] 页表 57 条 × 0x1000 |
| 计数器进位 | 128 位大端 +1 | [观测] `FUN_140059d70` |

> 因为 IV 只含页 VA、不含序号，**同页内容可离线复现**；这也是我们能完整解出 `.text` 的原因。

## 4. 执行流程

```
PE Entry (.AXJvbGt 内, 样本 0x61DC0)
  └─ entry: call stage1
       stage1 (FUN_14005a840)
         ├─ 校验 AKPH 魔数/版本
         ├─ 生成 32B 会话密钥（~T1^T2^k0^k1）
         ├─ AES-256-CTR 解密 stage2 → 0x63000(.PELvaOG)
         ├─ 校验 AKPC 魔数
         ├─ 构造 ctx（含函数指针表、flags、guard_interval）
         ├─ VirtualProtect(stub区, 0x200000, RWX)  ← 运行期改权限
         └─ 跳 stage2
               stage2
                 ├─ 逐条解析导入（哈希表 → API 指针 → 写 IAT@0x3A000）
                 ├─ 注册 VEH（接管页访问异常）
                 ├─ 建守护线程（FUN_140060550）
                 └─ 跳 OEP (AKPC+0x0C = 0x11B40 mainCRTStartup)
```

**惰性页解密**（`.text` 按页/按函数解锁）**[观测]**：
- 代码页初始为密文 + 不可执行/不可读；
- 访问异常进入 VEH，`p1 = (EXCEPTION_POINTERS*)`；若命中页表内的页，则调用 `FUN_14005d450(ctx, idx)`：
  1. `VirtualProtect(page, 0x1000, PAGE_READWRITE)`；
  2. `FUN_140059d70(key@ctx+0x58, IV(页VA), page, size)` 解密；
  3. `VirtualProtect(page, 0x1000, PAGE_NOACCESS)` 再上锁；
  4. 状态表 `state[idx] = 0`（已解密/可放行）。
- 页状态：`0`=已解密，`1`=上锁，`2`=待重加密/待处理（守护线程会扫描此状态）。

> 实测：我们 dump 时只有当前进程执行过的页是明文（50 多页），未执行的页仍是密文 —— 与本机制完全一致。

## 5. 保护机制实现细节

### 5.1 守护线程主循环（`FUN_140060550`）**[观测]**

```c
interval = ctx->config[+0x54];  if (interval < 200) interval = 200;   // 样本 2000ms
loop {
    Sleep(interval);
    if (flags & 0x1000000) {                 // 完整性/防篡改
        crc = CRC32(page_bytes);             // 用 CRC32 表 0x140059270
        check(ctx, "crc-const", state_byte, expected, crc, page_head);
    }
    if (detect_any(ctx) != 0)      response(ctx, 0x1004);   // FUN_14005fbb0
    if ((flags & 0x40) && check2()) response(ctx, 0x2000);  // FUN_140060710
    if ((flags & 0x03) == 0x03)    scan_threads(ctx);       // FUN_14005f900
    if (ctx->honeypot)             honeypot(ctx);           // FUN_140061040
}
```

### 5.2 硬件断点扫描（`FUN_14005f900`）**[观测]**

```
CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)
Thread32First/Thread32Next
  └─ 跳过本进程当前线程
     OpenThread(THREAD_SUSPEND_RESUME|THREAD_GET_CONTEXT)
       └─ SuspendThread → GetThreadContext(CONTEXT_DEBUG_REGISTERS)
            └─ 读 Dr0..Dr3（上下文里 local_800 字段），存 pageRVA = DrX - ImageBase
  └─ 恢复线程（ResumeThread）、CloseHandle
对每个 state==2 的页：
   └─ 若页范围 [VA, VA+0x1000) 命中某个 DrX → 视为"被调试器盯上"，跳过；
      否则 state=1 → FUN_14005d450 解密 → state=0
```

即：**用"线程调试寄存器是否指向受保护页"来检测硬件断点**，并且把"疑似被监控的页"保持密文。
对应配置项 `hwbp_check`、`relock_pages`。

### 5.3 反调试与异常检测（`FUN_14005fbb0`，2KB，按 flags 分项）**[观测/推断]**

开头即为位图分派：

```c
if ((flags >> 0x13 & 1) || (flags & 0x2b604) == 0) return false;   // 全部关闭则直接返回
lock: 只做一次（DAT_1400626c8 单次锁）
if (flags & 0x200)  {  // PEB 相关：通过 Self+0x60 取 PEB
     → NtGlobalFlag / BeingDebugged / 堆标志等经典检测
}
if (flags & 0x1000) {  // 另一组：与 ctx[0x1e] 回调相关的环境/模块检查
}
...
```

未逐位穷举的部分保持 [推断]：从 profile 项名（`antidebug / hwbp_check / int3_scan / anti_attach / timing_check / exception_check / hook_check / window_scan / kernel_debug / thread_hide`）可确认至少覆盖：
PEB 标志、进程调试对象、时序（rdtsc/QueryPerformanceCounter）、窗口/标题扫描、异常计数、模块/内存 hook 检测、`ThreadHideFromDebugger`。

### 5.4 响应分级（`FUN_1400603b0`）**[观测]**

| response 值 | 行为 |
|---|---|
| 3（或 flags&0x80000） | 通过回调上报字符串 **`"APK:tamper 0x%x"`**（便于开发期定位） |
| 1 | 走 `ctx->[0xd8]`（ExitProcess 一类） |
| 2 | **`int 0x29`（__fastfail(7)）** —— 不经过调试器的正常异常链，直接终止 |
| 0 / 其它 | 走 `ctx->[0xd0]` 回调 |

同时会置 `ctx+0x24c = 1`（"已触发"全局标记）并记录 `ctx+0x36c` 首次错误码。

### 5.5 导入表处理

- 默认（`obfuscate_imports=1`）：**清空 descriptors / ILT / IAT / names**，输出 PE 无导入表；stub 自己按"哈希表 → API 指针"重建 IAT。
- `obfuscate_imports=0`：保留原导入表，Windows 正常加载，stub 不重建。
- **[观测]** 桩内 API 表（样本 `.WQQJChj`，VA 0x67000）明文部分只有一条 bootstrap：

```
{ hash=0x40011B41, count=1, "KERNEL32.dll", "GetProcAddress", "VirtualAlloc" }
其余全部为高熵密文（运行时才解密成哈希→名字表）
```

即：先用 `VirtualAlloc+GetProcAddress` 起跳，再按哈希表批量解析（hash → 函数名 → GetProcAddress），因此常规 strings/导入表完全看不出它用了哪些反调试 API。

### 5.6 反 dump / 反内存转储

- 页级"解密→执行→重新上锁"，静态 dump 只能拿到已执行过的页（实测 57 页中 10 页仍是密文）；
- 页表带密文/明文双 CRC，改动代码页会被守护线程发现；
- `honeypot_pages`：配置里出现 honeypot 页与 `FUN_140061040` 蜜罐检查；
- `decoy_oep`：可放置假 OEP 诱骗"跳入口后 dump"的脚本；
- `randomize_sections` + `junk_sections`：节名/数量随机化，提高特征匹配难度；
- `erase_rich` / `strip_debug`：去掉 Rich 头与调试目录。

## 6. 强度评价

**做到的**
- 代码/数据页粒度的真实加密（AES-256-CTR，非 XOR），密钥按样本生成；
- 页表级 CRC 完整性 + 守护线程周期性复查；（中高强度）
- 硬件断点经调试寄存器检测（覆盖了"下 hwbp 断点"这类 dump 手法）；
- 导入混淆，静态看不出 API 集；
- 分级响应，含 `__fastfail` 这种不友好终止；
- 反 dump：未执行页保持密文。

**没做到的**
- 无虚拟化/无指令级混淆：一旦页解密，代码就是原始 MSVC 代码；
- 无内核态保护、无 inline hook、无自校验链；
- 所有开关集中在 `ctx+0x7C` 一个 dword，且 ctx 由 stage2 在**明文内存**里构造 → 一处 patch 全关；
- 守护线程是**单线程 while(true)**，把 `FUN_140060550` 改成 `ret` 或把 Sleep 拉长即可整体失效；
- 页 CRC 只覆盖页表列出的页；不动这些页、只在"未列入"的区域做修改可不触发；
- 明确限制：不支持 TLS 回调、要求 `SectionAlignment=0x1000`、仅 PE32+、加密区内不支持特殊重定位类型。

## 7. 绕过/脱壳要点（工程实践）

| 目标 | 最省力做法 | 备注 |
|---|---|---|
| 全量拿明文 | 复现 AES-256-CTR（key 由头内 4 字节+两表派生；IV=页VA） | 本仓库 `decrypt_text.ps1` 已验证与内存一致 |
| 关掉所有反调试 | 在 stage2 构造完 ctx 后把 `ctx+0x7C = 0` | 单点 |
| 关掉守护线程 | patch `FUN_140060550` 首字节 `C3`，或把 interval 改大 | 不影响程序功能 |
| 下断点而不被检测 | 不要用 hwbp/INT3；用 VEH/页守护或在 VEH 里改寄存器 | INT3 会改变页 CRC |
| 静态 dump | 必须在"目标页已执行"之后抓；否则补解密 | 未执行页仍是密文 |
| 干净 PE | 解密 .text + 重建导入表 + OEP=AKPC+0x0C | 见下节已知坑 |

### 已知坑（实测）
把 stub 去掉、入口改成 OEP 后，**Windows 加载器不会给原位于 `.rdata` 起始（0x3A000）的 IAT 回填**：
- 把描述符放 `.idata`/`.data`、把 `.rdata` 改可写、改 Import 目录大小、清 HEVA 均无效；
- 但把 `FirstThunk` 挪进 `.idata` 时加载器**开始处理**（会抛 0xC0000139，因压到字符串表）；
- 对照：正常 exe（IAT 在 `.idata`）走同一流程 → 可正常运行。
- 结论：要么保留 stub 只做导入解析（可用 `obfuscate_imports=1, encrypt_code=0` 生成"代码明文"版），
  要么把 IAT 迁到 `.idata` 并重定向 `.text` 内所有 RIP 相对引用。
